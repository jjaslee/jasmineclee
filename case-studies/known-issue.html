01 Overview

Known Issue is a curated apparel concept organized as a public name index.

Instead of allowing customers to enter arbitrary text, the system publishes predetermined designs associated with first names. Names become subjects, individual releases become records, and search becomes the primary way into the catalog.

I worked across product definition, information architecture, interaction design, visual language, and implementation in a custom Shopify Liquid theme.

How could a one-off name joke grow into a coherent catalog without becoming another customization tool?

02 From Joke to System

Known Issue began with a joke shirt I saw online: a line about dudes named Max doing the minimum.

The joke was memorable. The shirt itself felt disposable.

It seemed like something a person might receive as a gift, wear once, and stop reaching for after the punchline lost its novelty. I became interested in whether the premise could support a more considered garment—something that would still feel desirable after everyone already understood the joke.

At that stage, I was not thinking about records, indexes, or information architecture. I was thinking about better shirts, more names, and a coherent first release.

The system emerged when those individual products needed rules.

Why not customization?

The obvious product model already existed. On marketplaces such as Etsy, one reusable graphic can support almost any customer-entered name. That model solves availability, but it also makes each output feel interchangeable.

I chose predetermined releases instead.

That decision reduces immediate catalog coverage. Someone may search Known Issue and find nothing associated with their name. In return, each record can be treated as an authored product rather than a generated variation of the same template.

Customization is not permanently forbidden. It was excluded from the initial model because I wanted the first releases to establish what deserved to enter the catalog.

03 Product Model

“One name equals one shirt” would have worked for the first release, but it would have limited the system later.

Some names can support multiple references, ideas, and designed releases. I separated the name being indexed from the individual product being sold.

Search aliases can point alternate inputs toward the same subject rather than creating duplicate catalog entries. The structure leaves room for additional records without changing the underlying hierarchy.

Record IDs

The record ID began with an aesthetic reference. I was interested in the microtype, barcodes, and technical labels used across streetwear, but meaningless numbers would have been decoration pretending to be information.

I gave the detail a job. The same identifier can connect the garment, storefront, product information, and future releases.

04 Search + Directory

I designed around the product hypothesis that the visitor wants to know whether a particular name exists.

Most storefronts begin by asking what category of product someone wants. Known Issue instead treats the name as the primary discovery object.

A visitor can search directly for a subject, browse the public directory, filter the index alphabetically, open an individual name, and see all records associated with that subject.

Sarah       → match
SARAH       → match
  Sarah     → match

Sara        → no match
unless “Sara” is explicitly stored as an alias

In this system, a near-match is not simply a slightly worse search result. It may represent a different person entirely. Aliases resolve only when intentionally configured.

Browse A–Z

The directory provides a second route for visitors who do not arrive with a specific name. Available record counts can appear beside names, while the alphabet makes the catalog’s selectivity visible.

Grouped records

When one subject contains multiple records, they remain grouped under that subject rather than appearing as unrelated listings.

I have not yet tested whether real visitors instinctively begin with their own name or prefer to browse the available records first.

05 Missing Names

A selective catalog creates an immediate edge case: what happens when the searched name has no record?

The system does not fabricate a result, silently substitute another subject, or turn every failed search into an on-demand product. Automatic customization was deliberately not used as the fallback.

0 RECORDS FOUND communicates a real catalog state rather than a broken search.

Request Indexing

Consider this name for a future record.

A request does not mean a product has been ordered, the name will definitely be released, every request will be accepted, or a release date is promised.

Repeated requests could eventually become one input into release decisions, but this is not currently validated demand data. The request email and promotional opt-in serve separate purposes, so marketing consent remains a separate optional choice.

06 System Language

I initially explored an interface influenced by late-2000s and 2010s web conventions.

The appeal was partly cultural, but while designing the storefront I realized those conventions fit the product model naturally.

Indexes are built for looking something up, browsing known entries, distinguishing visited links, showing record counts, organizing items alphabetically, and communicating when an entry does not exist.

The reference therefore stopped being surface styling and began shaping the information architecture.

Functional metadata

Technical-looking details have to carry real information: record IDs identify records, status labels communicate availability, counts describe the directory, and links behave like links. IBM Plex Mono supports that system visually without becoming the decision itself.

07 Commerce Boundary

Use the record metaphor to organize the experience, not to make customers decode it.

Known Issue can describe products as records and names as subjects, but ordinary purchase actions remain recognizable. A shopper should not need to understand the metaphor in order to buy a shirt.

Purchase controls

Size, price, quantity, and Add to Cart use familiar labels and behavior.

Order information

Garment measurements, delivery estimate, shipping, product information, and return or final-sale terms remain direct.

The concept frames the transaction; it does not replace it.

08 Building + Iterating

Checkout, inventory, orders, and payment infrastructure were not the parts that made Known Issue distinct.

Rebuilding them would add risk without strengthening the product idea. I chose Shopify for the operational layer and built a custom Liquid theme for the differentiated behavior:

  • name-centered discovery
  • public directory
  • record grouping
  • controlled search
  • zero-result states
  • Request Indexing
  • the visual and interaction system

This kept custom work focused on the parts unique to the product.

AI-assisted implementation

I used Cursor and Codex heavily to accelerate implementation across Liquid, JavaScript, and CSS.

They helped translate interaction requirements into working behavior, investigate implementation problems, and shorten the distance between an idea and something I could test locally.

The product decisions remained mine: what a subject and record meant; how names should be organized; what search should return; what a missing result should offer; what Request Indexing could promise; where the archive metaphor should stop; and what changed after I used the implementation myself.

AI accelerated execution. It did not determine what Known Issue should become.

Implementation changed the model

Implementation exposed the need to distinguish subject_name, record_id, record grouping, related records, directory counts, and independent Shopify products.

An immediate promotional interruption also felt too loud when tested in context, so promotional asks moved later in the experience, after demonstrated interest.

09 Where It Landed

The current storefront establishes the core product system, but it should not be described as a validated commercial launch.

Implemented work includes:

  • a custom Shopify Liquid theme
  • first names as subjects and predetermined product records
  • structured record IDs
  • name search, aliases, and controlled matching
  • grouped subject results and an alphabetical directory
  • a designed zero-result state and Request Indexing interface
  • product and purchase pages with sizing, delivery, shipping, and product information
  • responsive behavior

Some screenshots may still come from theme preview, final product imagery may still be pending, the Shopify Forms production connection may still be pending, and a real subject containing multiple live records may still need to be demonstrated.

Commerce clarity

After launch, I would measure — future signals, not existing results

Search → record view · zero-result searches · Request Indexing submissions · repeatedly requested names · product → cart · cart completion · size-related questions · return reasons

The next step is not to add more metaphor. It is to learn where the existing metaphor helps—and where it needs to get out of the way.
